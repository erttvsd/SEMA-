# التشغيل والنشر

دليل تشغيل نظام «سِيمَا الخَيْر» في بيئة إنتاج: التهيئة الأولى، والإعدادات، والبريد، والتحقق بخطوتين،
والنسخ الاحتياطي والاستعادة، والنشر خلف وكيل عكسي، وقائمة التحقق قبل الإطلاق.

---

## 1. بيئة العرض وبيئة الإنتاج

| | العرض | الإنتاج |
|---|---|---|
| البناء | `npm run seed` — بيانات تصويرية كاملة وحسابات بكلمة `Sema@2026` | `npm run init` — المراجع النظامية فقط وحساب واحد للمدير التنفيذي |
| الحسابات في صفحة الدخول | ظاهرة | مخفية (`SEMA_DEMO=0`) |
| سرّ الجلسات | قيمة تطوير افتراضية | **إلزامي** (`SEMA_JWT_SECRET`) — والخادم يرفض الإقلاع بدونه مع `NODE_ENV=production` |
| البريد | يبقى «محتجَزاً» في الصندوق | يُرسَل عبر `SEMA_SMTP_URL` |

> لا تشغّل `npm run seed` على قاعدة إنتاج: يمحو كل شيء. و`npm run init` يرفض العمل على قاعدة فيها مستخدمون
> ما لم يُمرَّر `--force`.

## 2. التهيئة الأولى

```bash
npm ci --omit=dev
SEMA_DATA_DIR=/srv/sema/data npm run init -- --email director@example.ly --name "الاسم الكامل"
```

يبني الأمر قاعدة فيها كل المراجع النظامية — الأدوار التسعة عشر والصلاحيات الخمس والسبعون، والمستويات الخمسة
والشرائح الست وأرضياتها ورسومها، والمعايير الخمسة عشر، وأنواع الإثباتات، والمسارات المؤهلة، ومدونة المخالفات،
والمؤشرات ومستهدفاتها، وسجل المخاطر، والإعدادات — ثم حساب المدير التنفيذي الأول بكلمة مرور مؤقتة تُطبع مرة
واحدة (أو من `SEMA_ADMIN_PASSWORD`).

كلمة المرور الأولى **مؤقتة**: لا يصل صاحبها إلى أي شيء قبل تغييرها من «حسابي». والأمر نفسه يسري على كل حساب
تُنشئه الإدارة من «المستخدمون». بعدها:

1. فعّل التحقق بخطوتين لحسابك من «حسابي».
2. أنشئ حسابات الأمانة واللجان — والنظام يرفض أي تعيين يجمع بين وظيفتين متعارضتين (المادة 18)
   أو يخالف المواد 13 و22/1 و25.
3. من «الإعدادات» اجعل `require_2fa_internal = 1` لإلزام حسابات الحوكمة والأمانة بالتحقق بخطوتين.

## 3. متغيرات البيئة

النموذج الكامل في [`.env.example`](../.env.example).

| المتغير | إلزامي | الوظيفة |
|---|---|---|
| `NODE_ENV=production` | نعم | يفعّل فحوص الإنتاج ويعطّل خطافات الاختبار |
| `SEMA_JWT_SECRET` | نعم | سرّ توقيع الجلسات — 48 حرفاً عشوائياً على الأقل |
| `SEMA_PUBLIC_URL` | نعم | العنوان العام — تُبنى منه روابط رموز QR وروابط البريد |
| `SEMA_DEMO=0` | نعم | إخفاء الحسابات التصويرية |
| `SEMA_SMTP_URL` | للبريد | `smtps://user:pass@host:465` أو `smtp://…:587` |
| `SEMA_DATA_KEY` | مستحسن | مفتاح تشفير مفاتيح التحقق بخطوتين في القاعدة (وإلا اشتُق من `SEMA_JWT_SECRET`). **لا يُغيَّر** بعد التشغيل: تغييره يُبطل التحقق بخطوتين للجميع فتُسقطه الإدارة ويُعاد تفعيله |
| `SEMA_TRUST_PROXY` | خلف وكيل | عدد الوكلاء الموثوقين (عادةً `1`) — لازم لحدود المحاولات وسجل التتبع |
| `SEMA_DATA_DIR` | — | مجلد البيانات (الافتراضي `storage/`) |
| `SEMA_BACKUP_DIR` | — | مجلد النسخ الاحتياطية (الافتراضي `<DATA_DIR>/backups`) |
| `SEMA_JOBS_HOURS` | — | دورة المهام الآلية بالساعات (الافتراضي 6) |
| `SEMA_JOBS=0` | — | تعطيل المهام الآلية (للاختبار فقط) |
| `SEMA_REG_LIMIT` | — | حد التسجيل الذاتي لكل عنوان في الساعة (الافتراضي 10) |
| `PORT` | — | المنفذ (الافتراضي 3000) |

## 4. البريد الإلكتروني

كل رسالة تُقيَّد في **صندوق البريد الصادر** (النظام ← البريد الصادر) قبل إرسالها، فلا يضيع إشعار بتعطّل الخادم
البريدي:

- **الإشعارات**: كل إشعار داخل النظام تُرسل نسخته بالبريد، ما لم يوقفها المستخدم من «حسابي».
- **رسائل الأمان** — تغيير كلمة المرور، وتعيينها برابط، وتفعيل التحقق بخطوتين وتعطيله، واستعمال رمز استرداد —
  تصل دائماً ولا يوقفها التفضيل.
- **رسائل الاستعادة** تحمل رمزاً: متنها **لا يُحفظ في قاعدة البيانات أصلاً** — يبقى في ذاكرة الخادم حتى إرساله
  مرة واحدة، فلا يظهر في الصندوق ولا في أي نسخة احتياطية. وإن لم يكن خادم بريد مضبوطاً سُجِّلت «متعثرة» ولا
  تُعاد؛ يطلب صاحبها رابطاً جديداً بعد ضبطه.
- **الإشعارات السرّية** (البلاغات وملاحظات النزاهة) تخرج بالبريد عنواناً ورابطاً فقط، بلا نصها.
- بلا `SEMA_SMTP_URL` تبقى الرسائل العادية «محتجَزة»؛ وعند ضبطه تُرسلها المهمة الآلية «إرسال البريد المتعثر» أو زر
  «إعادة» في الصندوق. والمتعثرة تُعاد حتى خمس محاولات.
- الصندوق نفسه للمدير التنفيذي وحده (`admin.settings`): متون الإشعارات قد تحمل ما لا يطّلع عليه كل حامل لسجل التتبع.

## 5. الحساب والأمان

| الآلية | التفصيل |
|---|---|
| استعادة كلمة المرور | «نسيت كلمة المرور» ← رابط صالح **ساعة واحدة ولمرة واحدة**، ورمزه محفوظ ببصمته لا بقيمته، والرابط الجديد يُبطل ما قبله، والرد واحد وُجد الحساب أم لم يوجد. حدّ ثلاثة طلبات لكل بريد وعشرة لكل عنوان في الساعة |
| رابط من الإدارة | زر المفتاح في «المستخدمون» يُرسل الرابط إلى بريد صاحب الحساب — **لا تراه الإدارة** ولا تعرف كلمة المرور |
| كلمة المرور المؤقتة | ما تضعه الإدارة يلزم تغييره عند أول دخول، والخادم يرفض كل طلب آخر قبل ذلك |
| التحقق بخطوتين | TOTP قياسي (RFC 6238) يعمل مع أي تطبيق مصادقة، بنافذة ±30 ثانية، ويرفض إعادة استعمال الرمز، وثمانية رموز استرداد تُعرض مرة واحدة وتُحفظ ببصمتها. والمفتاح مخزَّن **مشفَّراً** (AES-256-GCM) بمفتاح خارج القاعدة |
| الإلزام | `require_2fa_internal = 1` يحجب حسابات الحوكمة والأمانة والمراجع الخارجي عن النظام حتى تُفعّله — ولا يملك تفعيل الإلزام إلا من فعّله لنفسه |
| فقدان الهاتف | الإدارة تُسقط التحقق عن الحساب بتسبيب مكتوب (يُقيَّد في سجل التتبع)، وتسقط جلساته، ويُبلَّغ بالبريد — ولا تفعل ذلك لنفسها |
| الجلسات | تسقط بتغيير كلمة المرور أو تعيينها أو تغيير الأدوار أو إيقاف الحساب أو إسقاط التحقق بخطوتين |

## 6. النسخ الاحتياطي والاستعادة

**النسخ**: لقطة متّسقة لقاعدة البيانات (`VACUUM INTO`) والخادم يعمل، مع فحص سلامتها وبصمتها SHA-256:

- تلقائياً مرة في اليوم (مهمة «النسخ الاحتياطي اليومي»).
- يدوياً من النظام ← النسخ الاحتياطي (صلاحية `admin.backup`: **المدير التنفيذي وحده**، لأن النسخة تحوي كل
  البيانات بما فيها البلاغات وما لا يطّلع عليه غيره)، بحد نسخة في الدقيقة، أو `npm run backup` من سطر الأوامر.
- النسخة لا تكفي للاستيلاء على حساب: كلمات المرور ببصمات bcrypt، ورموز الاستعادة ببصماتها، ومفاتيح التحقق
  بخطوتين مشفَّرة، ولا يُحفظ فيها أي رابط استعادة.
- يُحتفظ بآخر `backup_keep` نسخة (الافتراضي 14) وتُحذف الأقدم.
- التنزيل مقيَّد بالصلاحية ومقيَّد في سجل التتبع؛ فالنسخة تحوي بيانات شخصية ومستندات سرّية — احفظها
  مشفَّرةً خارج الخادم.

**المستندات المحمَّلة** (`<DATA_DIR>/uploads`) لا تدخل في نسخة القاعدة؛ تُنسخ بمزامنة المجلد، مثلاً:

```bash
rsync -a --delete /srv/sema/data/uploads/ backup-host:/backups/sema/uploads/
```

**الاستعادة** — والخادم متوقف:

```bash
systemctl stop sema          # أو: docker compose stop
SEMA_DATA_DIR=/srv/sema/data npm run restore -- /srv/sema/data/backups/sema-20260924-030000.db
# ثم استعد مجلد uploads المقابل زمنياً، وشغّل الخادم
```

يتحقق الأمر من سلامة النسخة وأنها قاعدة «سِيمَا الخَيْر» قبل أي تغيير، ويرفض العمل والخادم يعمل،
ويحفظ لقطة كاملة من القاعدة الحالية جانباً باسم `sema.db.before-restore-<الوقت>`. والخادم يُغلق القاعدة إغلاقاً
نظيفاً عند `SIGTERM` (أي `docker stop` و`systemctl stop`).

## 7. النشر بـ Docker

```bash
cp .env.example .env            # عبّئ القيم
docker compose build
docker compose run --rm sema npm run init -- --email director@example.ly --name "الاسم الكامل"
docker compose up -d
```

الصورة تعمل بمستخدم غير جذري، والبيانات في المجلد `/data` (مجلد Docker مسمّى `sema-data`)، وفيها فحص صحة
على `/api/health`. والمنفذ مربوط بـ `127.0.0.1` ليُنشر خلف وكيل عكسي.

## 7-ب. النشر على Dokploy بالنطاق semalibya.ly

**1) النطاق** — من لوحة المسجِّل (Libyan Spider ← Domains ← semalibya.ly ← DNS Management) أضف:

| النوع | الاسم | القيمة |
|---|---|---|
| `A` | `@` (أي semalibya.ly) | `169.58.44.17` |
| `A` | `www` | `169.58.44.17` |

إن كانت خوادم الأسماء (Nameservers) لدى جهة أخرى (Cloudflare مثلاً) فالسجلان يُضافان هناك. والانتشار يستغرق من دقائق إلى ساعات.

**2) الخدمة** — في Dokploy داخل المشروع: *Create Service ← Application*:
- *Provider*: GitHub ← المستودع `erttvsd/SEMA-` ← الفرع `claude/comprehensive-admin-system-qk7c3i` (أو `main` بعد الدمج).
- *Build Type*: **Dockerfile** (المسار `Dockerfile`).

**3) المتغيرات** — تبويب *Environment*:

```
SEMA_AUTO_SEED=demo
SEMA_DEMO=1
SEMA_PUBLIC_URL=https://semalibya.ly
```

هذا للعرض بالبيانات التصويرية. وللإنتاج الفعلي بدلاً منه:

```
SEMA_AUTO_SEED=init
SEMA_ADMIN_EMAIL=director@semalibya.ly
SEMA_ADMIN_NAME=الاسم الكامل
SEMA_ADMIN_PASSWORD=كلمة-مرور-مؤقتة-قوية-2026
SEMA_DEMO=0
SEMA_PUBLIC_URL=https://semalibya.ly
SEMA_SMTP_URL=smtps://user:pass@mail.semalibya.ly:465
```

`SEMA_JWT_SECRET` و`SEMA_DATA_KEY` اختياريان: إن لم يُضبطا وُلِّدا عند أول تشغيل وحُفظا في `/data` فيبقيان ثابتين.

**4) التخزين** — تبويب *Advanced ← Volumes / Mounts*: *Volume Mount* باسم `sema-data` على المسار **`/data`**.
بدونه تضيع البيانات والمستندات عند كل إعادة نشر.

**5) النطاق في Dokploy** — تبويب *Domains ← Add Domain*: Host `semalibya.ly`، Path `/`، Container Port **`3000`**،
HTTPS مفعَّل، Certificate **Let's Encrypt**. وكرّره لـ `www.semalibya.ly`.

**6) Deploy** — أول نشر يبني الصورة ثم البيانات (دقيقة تقريباً)، ويظهر في السجل
`نظام «سِيمَا الخَيْر» يعمل على …`. ثم افتح https://semalibya.ly.

> بديل: نوع *Docker Compose* بالملف `docker-compose.dokploy.yml` — المنفذ غير مربوط بالمضيف لأن لوحة Dokploy
> نفسها على المنفذ 3000، والنطاق يُضاف من *Domains* إلى الخدمة `sema` على المنفذ 3000.

## 8. الوكيل العكسي (nginx)

```nginx
server {
  listen 443 ssl http2;
  server_name sema.ly;
  ssl_certificate     /etc/letsencrypt/live/sema.ly/fullchain.pem;
  ssl_certificate_key /etc/letsencrypt/live/sema.ly/privkey.pem;
  add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
  client_max_body_size 21m;                 # المستندات حتى 20 ميجابايت
  location / {
    proxy_pass http://127.0.0.1:3000;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $remote_addr;   # قيمة واحدة يضعها الوكيل — لا يُمرَّر ما أرسله العميل
    proxy_set_header X-Forwarded-Proto $scheme;
  }
}
server { listen 80; server_name sema.ly; return 301 https://$host$request_uri; }
```

ومع هذا الإعداد: `SEMA_TRUST_PROXY=1`.

## 10. قائمة التحقق قبل الإطلاق

- [ ] `NODE_ENV=production` و`SEMA_JWT_SECRET` عشوائي طويل و`SEMA_DEMO=0`.
- [ ] `SEMA_PUBLIC_URL` على النطاق الفعلي، وHTTPS مفعَّل مع HSTS.
- [ ] `SEMA_SMTP_URL` مضبوط، وأُرسلت رسالة تجريبية ظهرت «مُرسَلة» في الصندوق.
- [ ] المدير التنفيذي غيّر كلمة المرور المؤقتة وفعّل التحقق بخطوتين، ثم `require_2fa_internal = 1`.
- [ ] نسخة احتياطية أُنشئت ونُزِّلت، وجُرِّبت استعادتها على خادم آخر، ومزامنة `uploads` مجدولة.
- [ ] `npm test` ناجح على النسخة المنشورة.
- [ ] الخطوات النظامية خارج النظام — تسجيل العلامة الجماعية، والرأي الضريبي — مكتملة (انظر الوثيقة 01، القسم 9).
